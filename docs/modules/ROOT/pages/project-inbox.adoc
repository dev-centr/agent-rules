The *project inbox* is DevCentr's second cross-org harness UX contract (after link:https://hci-nerdz.github.io/docs/hci-nerdz/grounded-tokens.html[grounded tokens / token provenance]).

In plain language: *when agents run parallel work, show a glanceable task grid — not a serialized wall of status spam in one chat scroll*.

== Problem

Multi-repo agent runs often produce one linear transcript:

* Repeated aggregate headers (`9 of 12 running…`) on every turn
* Done cards and blocked tasks interleaved with unrelated prose
* User must scroll backward to reconstruct which sub-job failed

The work is parallel; the surface is serial. Artifacts exist in some harnesses but sit *inside* the scroll instead of *beside* it as a durable progress monitor.

== Design direction

[cols="1,2"]
|===
| Principle | Meaning

| Parallel layout, serial storage
| One canonical chat thread on disk; the harness *routes* messages to task cards by topic. Forks are cosmetic views, not separate products of truth.

| Grid above thread
| Task cards live in a dedicated scroll region above (or beside) the main chat. The main thread stays aware of forks but does not replay every subagent line.

| Click-to-fork
| Each card opens a localized chat panel — the messages that pertain to that task only. Users can chat inside the subcontext.

| Chapters, not endless drift
| When coherence breaks, the user starts a *chapter*. The grid layout for the new chapter is immutable once issued; only cards that change in the new phase appear there. Prior chapters remain inspectable.

| Actor mailboxes
| Each task context maintains a state summary any sibling can read without interrupting its stream. Optional wait graph when one task must not analyze another's partial output.
|===

== Harness variable

[source,text]
----
PROJECT_INBOX = grid-forks | serialized | off
----

[cols="1,3"]
|===
| Value | Behavior

| `grid-forks`
| Emit task-card updates to the inbox grid; route detail lines to per-task fork views; main thread gets coordinator summaries only.

| `serialized`
| Today's default — all subagent lines land in the main scroll (compatible fallback).

| `off`
| Single-task mode; no grid chrome.
|===

Optional companion flags (proposed):

[source,text]
----
PROJECT_INBOX_CHAPTERS = on | off
PROJECT_INBOX_WAIT_GRAPH = enforce | warn | off
PROJECT_INBOX_CONTEXT_STORE = markdown-forks | struct-json | off
----

== Runtime model (implementation sketch)

=== Task context object

Each parallel job is a `TaskContext` — struct in memory, rendered to text per model invocation:

[source,json]
----
{
  "id": "merge-docs-3",
  "title": "Merge docs#3 onto main",
  "status": "done",
  "repo": "dev-centr/docs",
  "chapter": 1,
  "summary": "Merged; branch pushed; GitHub is source of truth.",
  "forkPath": "$CHAT_ROOT/forks/merge-docs-3.md",
  "siblingRefs": ["vscode-299941", "openshellorg-prohelp-1"],
  "waitOn": [],
  "lastEventAt": "2026-08-28T09:10:00Z"
}
----

=== Storage layout (proposed)

[source,text]
----
$CHAT_ROOT/
  thread.jsonl          # canonical append-only log (all messages)
  inbox/
    chapter-1.json      # immutable card layout snapshot
    chapter-2.json
  forks/
    merge-docs-3.md     # cosmetic view filtered from thread
    vscode-299941.md
  summaries/
    merge-docs-3.json   # actor mailbox — latest state for subscribers
----

The harness writes once to `thread.jsonl`, then projects into fork files and card summaries. Siblings read `summaries/*.json` at init — actor-style — without loading full fork transcripts.

=== Wait graph

When task B depends on task A's output:

* `waitOn: ["merge-docs-3"]` blocks B's model call until A's summary status is `done` or `failed`
* `warn` mode allows the call but tags the response as *partial dependency*
* Coordinator messages in the main thread explain blocked cards without duplicating every sub-line

=== Context compaction

When a fork exceeds token budget:

. Summarize the fork into a linked node (`summary-v2` → `summary-v1`)
. Keep sibling refs and chapter id in the summary header
. Main thread retains a one-line pointer: "fork `merge-docs-3` compacted — see summary-v2"

== Coordinator vs many-top-level bots

Two valid deployment shapes:

*Hierarchical (default):* one coordinator bot spawns task contexts; grid is the coordinator's inbox.
*Many-to-many (alternate):* task contexts live outside chat entirely; user messages specific coordinator bots that share mailbox paths. Same storage layout; different UI entry points.

DevCentr's first harness iteration targets hierarchical mode; the storage model does not forbid the alternate schema.

== What this is not

* Not a replacement for grounded tokens — use both: provenance on *words*, inbox on *jobs*
* Not true multi-threaded git — one log, many views
* Not Cursor's Task tool UI — this is harness-neutral metadata DevCentr emits regardless of host
